## 5. Architecture Decisions

- Header is **page-specific**, not global
  - Home page: Logo 3 + ThemeToggle (simple)
  - Components pages: `Header` component with Logo 3 + search + nav + ThemeToggle
- Search bar lives in Header component, accepts `searchValue`/`onSearchChange`/`showSearch` props
- Component cards link to their showcase pages via `componentRoutes` mapping
- All showcase/temp files go in `apps/web/src/_showcase/` — entire folder + `/components` page to be deleted after project completion
- **No third-party CDNs** — all assets must be self-hosted or downloaded locally
- **Flutter checkbox dropdown** — fully controlled component pattern (parent owns state, component calls onChanged)

## 10. Admin Dashboard (2026-09-22)

### 10.1 Overview
Full Next.js admin dashboard built from scratch with real authentication, API integration, and advanced responsive layout matching the reference project.

### 10.2 Authentication System
- **Login**: `admin@telnd.com` / `admin12345` → JWT → dashboard
- **JWT**: `hono/jwt`, 7d access / 30d refresh tokens, bcrypt password hashing
- **Session**: Stored in DB, cookie-based middleware protection
- **Auth context**: `useAuth()` hook, login/logout, token persistence (localStorage + cookies)
- **Middleware**: Server-side route protection, redirects unauthenticated to `/login`, authenticated away from `/login`

### 10.3 API Server (`packages/api`)
- Standalone server via `@hono/node-server` on port 3001
- Auth routes: real bcrypt comparison, JWT signing, session creation, `lastLoginAt` update
- Rate limiter: Redis-backed with graceful fallback when Redis unavailable
- CORS: configured for ports 3000, 3001, 3002
- Dev mode: returns actual error messages for debugging

### 10.4 Admin App (`apps/admin`)

### 14.2 Permission model & API middleware
- Flat string grants on `AdminRole.permissions`: `"resource.action"` (e.g. `admins.delete`) or `"*"` wildcard (super admin bypass); validated by `/^(\*|[a-z][a-zA-Z0-9]*(\.[a-z][a-zA-Z0-9]*)+)$/`
- `middleware/auth.ts` gained `requireAdmin`, `hasPermission`, `requirePermission(...)`, `requireAnyPermission(...)` (suspend/activate accepts `users.edit` **or** `admins.edit`)

### 14.3 API routes

**§14.40 follow-up 5 — ROOT CAUSE of the stuck "Not enabled": responses had no `Cache-Control`**

## §14.47 Unified sign-in-or-create + two-door account separation (2026-10-01)

- **Account-type standard (the rule everything now enforces)**: one account, one role (`UserRole`) — CANDIDATE/EMPLOYER/CREATOR/FREELANCER/AGENCY are portal roles, ADMIN is a panel role, and nothing ever holds two. Three doors: the **admin panel** admits only ADMIN accounts that also have an **active `AdminUser`** profile (the API's existing `roleGuard('ADMIN')`/`requireAdmin`/`requirePermission` layer keeps guarding every route); the **user portal** admits every non-ADMIN role (EMPLOYER is a portal role, not its own login); ADMIN is never creatable, and never signed in, through a portal path. New helper **`doorError(user, context)`** in `routes/auth.ts` is the account-side verdict: `context:'admin'` + non-ADMIN (or ADMIN without an active `AdminUser`) → 403 `NOT_ADMIN` (two wordings for the two cases, one code — probing never distinguishes them); `context:'portal'` + ADMIN → 403 `ADMIN_ACCOUNT`. It runs only **after the credential proved itself** (password/OTP verified, lockout reset), so a disabled door is never a pre-auth oracle.
- **`context` rides the whole challenge**: `loginSchema` gains an optional `context: 'admin' | 'portal'` (absent = legacy behaviour — older clients and the existing suites skip the check and grant nothing new); `/login` applies `doorError` at step 6a and stores the claim **inside the `telnd_2fa_pending` token**; `readPendingTwoFactor` returns it; `/2fa/challenge/verify` re-applies `doorError` **before any attempt is counted** and clears the pending cookie on refusal — a challenge minted on one portal can never close on the other (proved by forged-HS256-pending E2E below). `/login-link/verify` applies the portal verdict before spending the token, so an admin's magic link is refused with the link left intact. The admin frontend sends `context:'admin'`, and a session whose `/auth/me` answer carries `adminRole: null` is dropped as unauthenticated (`refreshUser`), likewise `completeLogin` (host-scoped cookies mean a portal 2FA pending lands on `:3002/2fa` too — it refuses, logs the session out, bounces to `/login`).
- **Login ≡ signup — no account found starts creating it**: the legacy `POST /api/auth/signup` (which mangled `passwordHash` into `password` and created unverified accounts with zero channel proof) is **deleted**, its `publicPaths` entry replaced by the two new endpoints. `/login` with an **unknown email + password** now: checks the `email` switch (creation obeys the same gates as sign-in — a disabled method answers 403 `METHOD_DISABLED` without minting anything), bcrypt-hashes the password (12), mints a signup intent, emails `sendSignupVerifyEmail` (new template: verify-once link to `/auth/verify-email?token=…`, 30-minute lifetime, "doing nothing creates nothing"), and answers 200 `{requiresEmailVerification}` — production discards the intent if delivery fails (generic answer preserved); **outside production the response also carries `devVerifyUrl`** so the flow is exercisable without SMTP. `/login` with an **unknown phone + OTP**: the code lives in a new **phone-keyed OTP entry** (`phone:<number>`, same store/rules as account codes — 5-minute TTL, 5 wrong tries, 45-second gap, purpose `'login'`, new `sendOtpToPhone`), a correct code answers `{requiresProfile, signupToken}`. `/login-link` for an unknown address mints a `channel:'link'` intent and sends the same create-account mail — the response stays byte-identical to the known-account branch (the dev hook excepted, which the portal-auth suite strips before comparing).
- **`packages/api/src/lib/signupIntents.ts`** (new): in-memory like every auth ephemeral here — 30-minute TTL, single-use, **one live intent per identifier with latest-request-wins rotation** (a squatter's link for someone else's address dies when the real owner asks — pre-registration attacks are worthless), keyed by token **SHA-256** (the raw token exists only in the mailed link), only the bcrypt hash inside, resend budgets for the emailed channels (one per minute, five per hour — `/login` with unknown addresses can never be a mail cannon; the phone channel skips them because its OTP gap and the route limit are the throttle), plus a hard identifier cap that trims the oldest half.
- **Finish screen — `POST /api/auth/signup/check` + `POST /api/auth/signup/complete`** (public, 20/min + 5/min): `check` *peeks* (reloads must not burn the token) and answers what the token opens — `valid` + `channel` + masked identifier, `accountExists: true` when another door won the race since mint, 401 `SIGNUP_TOKEN_INVALID` for dead/garbage tokens — re-reading its method switch so a method disabled after the email went out still can't mint an account. `complete` peeks for the gate, then **takes** (strict single-use: rival tab/replay → 401), refuses `USER_EXISTS` 409 (pre-check and `P2002` race both), creates the account **`role:'CANDIDATE'`**, `isEmailVerified` for email/link channels, `isPhoneVerified` for phone (the channel that proved it *is* the verification), pre-registers the login device (no "new device" alert at birth, exactly like the retired signup flow), then `issueSession` — same session cookies as any other sign-in.
- **Portal** (`apps/web`): `/auth/email-password` sends `context:'portal'` and renders a status box on `requiresEmailVerification` ("No account for *x* yet — we sent a verification link… the password you just typed becomes your new password"); `/auth/otp` sends `context:'portal'` and routes `requiresProfile` to the new **`/auth/verify-email`** page (`AuthFrame` + top bar; modes: checking spinner → form "Create your account" with the masked identifier and first/last name → `complete` → `/`; `exists` → "You already have an account — sign in instead"; `invalid` → plain refusal, both with a Back-to-sign-in button; `SIGNUP_TOKEN_INVALID`/`USER_EXISTS` mid-submit flip the mode, `METHOD_DISABLED` shows the message). `login-link`'s existing error surface shows `ADMIN_ACCOUNT` as-is.
- **Verification**: tsc — `packages/validation` **0**, `packages/api` **0**, `apps/admin` **0**, `apps/web` at its 2 pre-existing baseline errors. New E2E **`/tmp/opencode/verify_unified_auth.ts` — 31/31** on first run: door rules (candidate→`NOT_ADMIN`, admin→`ADMIN_ACCOUNT`, ADMIN-without-profile→`NOT_ADMIN` "active administrator profile" wording, real admin→200 with the throwaway `adminRole`), method gates governing **creation** (known-wrong-password still plain 401 while email is off — no oracle; unknown + off → `METHOD_DISABLED`), email intent mint → throttle (retry inside the gap: same answer, **no** new link) → check (masked identifier) → complete (session, CANDIDATE, `adminRole:null`, `/me` shows `isEmailVerified:true`) → single-use 401s → raced-account `accountExists`/409 → garbage 401 → the created account logging in through the normal path; magic-link create (generic message identical both branches, dev URL only on the unknown one, link-channel account born verified, admin's link 403 + token **not** spent); three **forged `telnd_2fa_pending`** challenges (admin-for-portal → 403 *before* any code check, candidate-for-admin → 403 `NOT_ADMIN`, candidate-on-own-door → passes the door and fails the factor `TWO_FACTOR_UNAVAILABLE`); phone leg's wrong-OTP 401 after a 61-second rate-window wait (the positive OTP path needs a real gateway send — out of suite scope, documented in its header; the phone-keyed store shares every OTP rule). ## §14.50 Browser-report round: first-click 429 + retry countdown, retry focus, spinner audit, optional profile phone (2026-10-02)
